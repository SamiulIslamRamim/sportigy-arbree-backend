# Sportigy Arbree — Backend API

Express 5 + TypeScript backend for **Sportigy**, a multi-sport platform where players self-report matches, admins create the sport hierarchy and review/approve match submissions, and career statistics are computed live from approved match data.

This README documents the current state of the project: setup, architecture, response/error conventions, the sport hierarchy setup, match self-report + admin approval, and career statistics + team visibility.

## Response Envelope

**Every** endpoint returns the same envelope:

```json
// success
{ "success": true, "message": "Login successful.", "error_code": null, "data": { } }

// error
{ "success": false, "message": "Invalid mobile number.", "error_code": 1306, "data": {} }
```

- `error_code` is a JSON number when numeric, `null` on success.
- HTTP status is always derived from `ERROR_STATUS_MAP` (via `AppError` / `ResponseHandler`).

---

## Error Handling

- Controllers have **no try/catch**. They are wrapped in `asyncHandler`; rejections flow to `next(err)`.
- Errors are raised with `throw new AppError(ERROR_CODES.X)` — message + HTTP status are auto-resolved from the constants.
- `errorHandler` order: `AppError` → `ZodError` (→ `1402 FIELD_VALIDATION_FAILED` with `err.flatten()`) → `PrismaClientKnownRequestError` (→ mapped via `PRISMA_ERROR_MAP`) → `1000 APP_SERVER_ERROR` (real error logged server-side only).

## Data Model

- **User** — players & organizations (`role` enum, `isActive`).
- **Admin** — DB-backed, bcrypt hash.
- **Sport hierarchy** — `Sport` → `SportCategory` / `SportField` / `SportFieldOption`.
  - `SportField`: `section` `PROFILE|MATCH`, `type` `SELECT|MULTI_SELECT|NUMBER|TEXT|BOOLEAN|DATE`.
  - `SportFieldOption`: for `SELECT`/`MULTI_SELECT` only.
  - `SportMetric` — named buckets (`Batting`/`Bowling`, `Offensive`/`Goalkeeping`) that `SportField.metricId` points at; fields with no metric show under `Other`.
  - **Computed fields** — `SportField` with `isComputed: true` (NUMBER + MATCH only). Value is derived, never player-entered: `SUM(numerator) ÷ SUM(denominator) × formulaMultiplier`. `SportFieldFormulaComponent` rows (`NUMERATOR`/`DENOMINATOR`) reference raw source fields only (no chaining).
- **PlayerSportProfile** → **PlayerFieldValue** (option-only profile answers).
- **PlayerMatch** → **PlayerMatchFieldValue** — the **merged match + participation** record.
  - A player's own full match: title, venue, teams, result, and per-field stat values.
  - `status`: `PENDING | APPROVED | REJECTED`, plus `reviewedBy` / `reviewedAt` / `rejectReason`.
  - `PlayerMatchFieldValue` is **typed per field type**: `optionId` (SELECT/MULTI_SELECT), `valueNumber` (NUMBER, `Decimal(12,4)`), `valueText`, `valueBoolean`, `valueDate`.
  - Composite index `[userId, sportId, status]` serves the statistics endpoints.
- **PlayerTeamVisibility** — one row per `(player, sport, team)`; **presence = hidden**, DELETE = unhide. `teamKey` unifies verified + free-text teams.

## Sport Hierarchy & Setup (admin)

Admin builds the sport tree before players can register or submit matches. **The order matters:** create the sport → its categories (formats) → its fields → then options for `SELECT`/`MULTI_SELECT` fields.

### Setup flow

```
 1. POST /admin/sports/                          → create the sport
 2. POST /admin/sports/:sportId/categories/      → create formats (T20, ODI, 11-a-side)
 3. POST /admin/sports/:sportId/metrics/         → optional: create metric buckets (Batting, Bowling…)
 4. POST /admin/sports/:sportId/fields/          → create fields (PROFILE / MATCH sections)
 5. POST /admin/fields/:fieldId/options/         → options for SELECT/MULTI_SELECT fields
```

### 1. Create a sport — `POST /admin/sports/`

```json
{ "name": "Cricket", "description": "Bat and ball sport" }
```

`slug` is auto-generated from `name` when omitted. Duplicate `name`/`slug` → `1407`.

### 2. Create categories — `POST /admin/sports/:sportId/categories/`

```json
{ "name": "T20" }
{ "name": "ODI" }
```

### 3. Create fields — `POST /admin/sports/:sportId/fields/`

A **PROFILE** field (e.g. playing role), with its options nested in one request:

```json
{
  "name": "Playing Role",
  "section": "PROFILE",
  "type": "SELECT",
  "options": [
    { "label": "Batsman" },
    { "label": "Bowler" },
    { "label": "All-rounder" }
  ]
}
```

A **MATCH** numeric field (drives career stat sums):

```json
{
  "name": "Runs",
  "section": "MATCH",
  "type": "NUMBER",
  "description": "Runs scored in the match",
  "metricId": "6a1e...-uuid-of-Batting-metric"
}
```

A **computed** MATCH field (never player-entered, derived via formula):

```json
{
  "name": "Strike Rate",
  "section": "MATCH",
  "type": "NUMBER",
  "isComputed": true,
  "formulaMultiplier": 100,
  "metricId": "6a1e...-uuid-of-Batting-metric",
  "formulaComponents": [
    { "sourceFieldId": "…runs-field-id…", "role": "NUMERATOR" },
    { "sourceFieldId": "…balls-faced-field-id…", "role": "DENOMINATOR" }
  ]
}
```

Notes:
- `section` is `PROFILE` or `MATCH`; `type` is `SELECT | MULTI_SELECT | NUMBER | TEXT | BOOLEAN | DATE`.
- `options` (nested create) is only allowed for `SELECT`/`MULTI_SELECT` → otherwise `1401`.
- Uniqueness is `(sportId, section, slug)` → duplicates → `1407`.
- A computed field must be `section: MATCH`, `type: NUMBER`, and `required` is always forced `false`. It needs **at least one** `NUMERATOR` and one `DENOMINATOR` component.
- Each component's `sourceFieldId` must belong to the **same sport**, be `section: MATCH`, `type: NUMBER`, and `isComputed: false` (no chaining). A field can't reference itself → `1401`. Duplicate `(sourceFieldId, role)` → `1407`.
- `metricId` (computed or not) must belong to the sport → otherwise `1401`.

### 4. Create options — `POST /admin/fields/:fieldId/options/`

```json
{ "label": "Right-arm Fast" }
```

`value` is auto-generated from `label`. Unique per field → `1407`.

## Match Self-Report + Admin Approval

`PlayerMatch` is a single merged table: each submission is the player's full match (title, venue, teams, result, stats). There is **no separate `Match` table** — a "one real match, many players" join model is flagged as a future migration.

> Protected routes require `Authorization: Bearer <accessToken>`. Admin routes additionally require an admin token.

### Player endpoints

All under `/player/matches/...`, guarded by `authenticate`.

| Method | Route | Purpose |
|--------|-------|---------|
| POST | `/player/matches/` | submit a match (status `PENDING`) |
| GET | `/player/matches/` | list all of my matches |
| GET | `/player/matches/approved/` | filter by status |
| GET | `/player/matches/pending/` | — |
| GET | `/player/matches/rejected/` | — |
| GET | `/player/matches/:matchId/` | match detail (values + team orgs resolved) |
| PATCH | `/player/matches/:matchId/` | edit while `PENDING` or `APPROVED` (reset → `PENDING`) |
| DELETE | `/player/matches/:matchId/` | withdraw while `PENDING` only |

> Route ordering matters: the literal `approved/`, `pending/`, `rejected/`, `stats/...`, and `team-visibility/...` segments are registered **before** `/:matchId/` so they are not swallowed by the param.

### Create match — `POST /player/matches/`

```json
{
  "sportId": "0b6d4e9a-...",
  "sportCategoryId": "3f1a9c2b-...",
  "title": "Summer League Round 4",
  "tournament": "Summer League",
  "matchType": "League",
  "venue": "Arbree Ground",
  "homeTeam": { "name": "Bengal Tigers" },
  "awayTeam": { "orgId": "c5a2d7f1-..." },
  "matchDate": "2026-08-01T14:00:00.000Z",
  "result": "WIN",
  "playerSide": "HOME",
  "isCaptain": true,
  "isSubstitute": false,
  "minutesPlayed": 90,
  "notes": "Scored the winning goal.",
  "values": [
    { "fieldId": "a1b2c3d4-...", "valueNumber": 34.5 },
    { "fieldId": "b2c3d4e5-...", "optionId": "c3d4e5f6-..." }
  ]
}
```

Team slots accept either a free-text name (`string` or `{ "name": "..." }`) or a verified organization (`{ "orgId": "..." }`). `playerSide: "HOME"`/`"AWAY"` must point at a non-empty team — otherwise `1401`.

**Stat value channels** — each `fieldId` must be an active `MATCH` field of the sport, and the value channel must match the field `type`:

| Field type | Use |
|------------|-----|
| `SELECT` / `MULTI_SELECT` | `optionId` |
| `NUMBER` | `valueNumber` (decimal allowed) |
| `TEXT` | `valueText` |
| `BOOLEAN` | `valueBoolean` |
| `DATE` | `valueDate` |

Duplicate `fieldId` in `values` → `1407`. A `MULTI_SELECT` field stores only one option (`@@unique([playerMatchId, fieldId])` caveat).

### Update match — `PATCH /player/matches/:matchId/`

Same fields as create, all optional. `REJECTED` is locked → `1701`. Editing an `APPROVED` match resets `status` to `PENDING` for re-review. `values` uses **replace-all** semantics: omitted → untouched; sent → old set deleted, new validated set created. Empty body → `1408`.

Team consistency is validated against the **effective side** (`body.playerSide ?? existing.playerSide`) — clearing a team while the existing side still references it → `1401`.

### Admin review endpoints

All under `/admin/matches/...`, guarded by `authenticateAdmin`.

| Method | Route | Purpose |
|--------|-------|---------|
| GET | `/admin/matches/?status=PENDING` | review queue (filter optional) |
| GET | `/admin/matches/:matchId/` | full detail incl. submitting player |
| PATCH | `/admin/matches/:matchId/approve/` | set `APPROVED` + `reviewedBy`/`reviewedAt` |
| PATCH | `/admin/matches/:matchId/reject/` | set `REJECTED` + `reviewedBy`/`reviewedAt`/`rejectReason` |

`PATCH /admin/matches/:id/reject/` body:

```json
{ "reason": "Incomplete scorecard — missing 2nd innings figures." }
```

Re-doing the **same** status → `1701`. Cross-state override (`REJECTED→APPROVED`, `APPROVED→REJECTED`) is allowed for admins.

## Career Statistics + Team Visibility

Two **read-only** endpoints compute career stats **live** from `status == APPROVED` `PlayerMatch` rows — there is no stats source-of-truth table. A small `PlayerTeamVisibility` table backs the hide/unhide feature.

### 1. Career summary by category

`GET /player/matches/stats/career/?sportId=<uuid>`

Filters the player's matches to `sportId` + `APPROVED`, groups by `sportCategoryId` (`null` → `Uncategorized` bucket), and returns per group: `matchesPlayed`, a `resultBreakdown` (counts per `MatchResult`), and a `metrics` array (Phase 6). Each metric bucket carries its name (`metric`), `metricId` (`null` for the `Other` bucket) and a `fields` list. Raw `NUMBER` MATCH fields produce `{ fieldId, name, isComputed: false, total }`; computed fields produce `{ fieldId, name, isComputed: true, value }`.

### 2. Career by team — with hide/unhide

`GET /player/matches/stats/by-team/?sportId=<uuid>&hidden=include|exclude`

Same aggregation shape, but grouped by the **player's team** — derived per row from `playerSide` (either `homeTeam`/`homeTeamOrgId` or `awayTeam`/`awayTeamOrgId`). Rows with `playerSide == null` are excluded (nothing to group by).

- `hidden=include` (default) → returns **every** team with an `isHidden` flag, so the frontend can render a "hidden teams" section.
- `hidden=exclude` → visible teams only (the main view).


`teamKey` unifies verified + free-text teams into one comparable value:

- `org:<uuid>` — when the side's `*OrgId` is set
- `name:<lowercased trimmed name>` — free-text teams

The `teamKeyFor()` (helper.ts) and the SQL `CASE` in `buildSideCte` (player-careerStat.controller.ts) **must stay in sync**.

### 3. Hide / unhide a team

Hiding affects **only the by-team page** — category totals on the career summary are unaffected.

`POST /player/matches/team-visibility/` — hide (idempotent):

```json
{ "sportId": "0b6d4e9a-...", "teamName": "Bengal Tigers" }
// or
{ "sportId": "0b6d4e9a-...", "teamOrgId": "c5a2d7f1-..." }
```

Exactly one of `teamOrgId` / `teamName` is required (else `1408`). For `teamOrgId`, the org must exist, be active, and have `role === organization` (else `1401`).

`DELETE /player/matches/team-visibility/` — unhide (idempotent, same body):

```json
{ "sportId": "0b6d4e9a-...", "teamName": "Bengal Tigers" }
```

Presence of a `PlayerTeamVisibility` row means **hidden**; DELETE removes the row (no boolean column).

### Stats computation

- Computed live — a stats table is never written.
- **Only `APPROVED` matches count** (`PENDING`/`REJECTED` excluded).
- **2 grouped queries per endpoint**, never one-per-field:
  1. group-level query → `matchesPlayed` + result pivot (`COUNT(*) FILTER`)
  2. `(group, field)` query → `SUM(value_number)` per numeric MATCH field
- Numeric totals are `SUM` over `PlayerMatchFieldValue.valueNumber` (`Decimal(12,4)`) — exact, no float drift. No per-field aggregation-type config yet (straight sums).
- **Computed fields (Phase 6)** — the grouped query is unchanged; it already returns `SUM(valueNumber)` per raw `NUMBER` field per group. A post-processing step then, **per group**, reads each computed field's numerator/denominator components' sums out of that same result set, **sums first, divides once at the end**, and applies `formulaMultiplier`: `value = Σ numerator ÷ Σ denominator × multiplier`, or `null` when the denominator is zero/missing (e.g. `0` balls faced → no strike rate). `isComputed` fields carry no `PlayerMatchFieldValue` rows (filtered from the player's form), so nothing to store.
- Raw fields that are also formula inputs still appear on their own — being a component doesn't hide a field.
- The by-team endpoint derives the team from `playerSide` inside a SQL CTE; raw `$queryRaw` is used where native PG enums need `::"EnumName"` casts.
- Backed by composite index `[userId, sportId, status]`.

## Sport Metrics & Computed Fields (Phase 6)

Both are admin-configurable per sport (sports themselves are admin-created).

### Metrics

A `SportMetric` is a named group a `SportField` belongs to (`Batting`/`Bowling` for cricket, `Offensive`/`Goalkeeping` for football), so career stats break down by metric instead of one flat field list. A field's `metricId` is nullable — fields without one fall under an `Other` bucket in the stats response. Assigning metrics is retroactive; no backfill required.

- Create/list under `/admin/sports/:sportId/metrics/`; update/delete under `/admin/metrics/:metricId/` (all `authenticateAdmin`).
- `slug` auto-generated from `name`; unique per sport → `1407`.
- DELETE is a **soft delete** (`isActive: false`); it also detaches any fields currently assigned to the metric (`metricId → null`, since the FK is `SetNull`).

### Computed fields

A `SportField` with `isComputed: true` whose value is **never entered by the player** — it is derived as `SUM(numerator fields) ÷ SUM(denominator fields) × formulaMultiplier`. Computed fields reference **raw inputs only** (a source field can't itself be computed), so evaluation is single-pass with no dependency ordering.

- `type` forced `NUMBER`, `section` forced `MATCH`, `required` forced `false`.
- Needs ≥1 `NUMERATOR` and ≥1 `DENOMINATOR` component; no self-reference; every source field in the same sport (`MATCH` + `NUMBER` + not computed).
- Computed fields are excluded from the player's match-entry form — `validateMatchValues` filters `isComputed = false`, so no `PlayerMatchFieldValue` row is ever written for them.
- Career aggregation: the Phase 5 grouped query is unchanged; computed values are derived in post-processing from the already-summed raw totals, **sum-then-divide-once**, per group. A "strike rate" is `Σ runs ÷ Σ balls × 100`, never the average of per-match strike rates.

```json
// GET /player/matches/stats/career/ — per category (abridged)
{
  "categoryId": "…",
  "categoryName": "T20",
  "matchesPlayed": 12,
  "resultBreakdown": { "WIN": 7, "LOSS": 4, "TIE": 1, "DRAW": 0, "NO_RESULT": 0 },
  "metrics": [
    {
      "metric": "Batting",
      "metricId": "…",
      "fields": [
        { "fieldId": "…", "name": "Runs", "isComputed": false, "total": 450 },
        { "fieldId": "…", "name": "Balls Faced", "isComputed": false, "total": 320 },
        { "fieldId": "…", "name": "Strike Rate", "isComputed": true, "value": 140.63 }
      ]
    },
    { "metric": "Bowling", "metricId": "…", "fields": [ ] }
  ]
}
```

> Known limitation: `formulaMultiplier` is per computed field only — a per-component weight (e.g. "total bases = singles + 2×doubles") would need a follow-up. Nothing currently requires it.

## Flows

### Match → stats pipeline

```
Admin: POST /admin/sports/ ─► POST /admin/sports/:id/categories/ ─►
       POST /admin/sports/:id/metrics/ ─► POST /admin/sports/:id/fields/ ─►
       POST /admin/fields/:id/options/

Player: POST /player/matches/ (PENDING)
   └─► Admin: GET /admin/matches/ + approve/reject
         └─► APPROVED rows feed:
               GET /player/matches/stats/career/
               GET /player/matches/stats/by-team/?hidden=include
   Player: POST/DELETE /player/matches/team-visibility/ ─► toggles isHidden per team
   Computed fields (e.g. SR) are derived server-side from raw sums.
```

### Role ownership

- **Admin** owns: sport hierarchy (Sport/Category/Metric/Field/Option), match review + stat approval.
- **Player** owns: profiles, match entries (self-reported, pending admin approval), team visibility preferences.
